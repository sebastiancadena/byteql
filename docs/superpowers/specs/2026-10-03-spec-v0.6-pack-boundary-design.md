# Spec v0.6: the pack boundary

Date: 2026-10-03

Status: proposed design, pre-implementation. Nothing in this record is built yet.

Source: the 2026-10-03 architecture review and its cleanup plan
(`docs/superpowers/plans/2026-10-03-architecture-cleanup.md`, Task 12). Roadmap: the
prerequisite for priority 6, "Ship one forensic investigation workflow" (`ROADMAP.md`), whose
preferred format, EVTX, is this design's acceptance case.

## Purpose

The pack kit (`2026-09-23-pack-kit-design.md`) made a format pack a manifest, a projection spec,
queries, and a few named code hooks. The boundary between those hooks and the engine still
leaks in both directions:

- **Packs encode engine mechanics.** Framers name spec tables, MIDI builds sparse arrays to make
  state registers reset, and ZIP and pcap omit object keys so that an anchor does not match a
  `null`.
- **The engine encodes format knowledge.** IP-address, DOS-date, and 24-bit integer helpers live
  in core's closed builtin set. The SYN retransmission and adoption rules sit in the generic
  stream runtime. Engine flow fields silently overwrite key-extractor fields of the same name.
- **Engine-owned outputs have no single definition.** The segments and `errors` tables are
  special-cased in four places. `errors` is built through a second Arrow path. Issues are kept
  without a bound and shipped to the app twice.

Spec v0.6 closes those leaks so that a new pack, starting with EVTX, needs **zero edits to
`packages/core`**. The migration bar for MIDI, ZIP, and pcap is the pack kit's: **golden-identical
Arrow output and schema-identical `pack.schemas()`**.

## Scope decisions

- **One spec version, several independent slices.** Each slice stands alone and ships with its
  own green gate. The spec-surface slices (record kinds, per-record reset, null anchors) share a
  version bump. The others (output tables, issues, builtins, version floor, hygiene) are engine
  refactors that every supported spec version gets.
- **The data-first direction stays.** Every new mechanism is either declared in the spec, or is
  a named hook whose names the spec references and `byteql-pack build` types. No new mechanism
  is "code the engine calls without the spec saying so".
- **No silent behavior changes for supported specs.** v0.6 semantics (null anchors, record
  kinds) apply only to specs that declare `version: '0.6'`. Where an engine change affects every
  version, this record says so and justifies it.
- **Minimum supported spec version becomes 0.4.** Versions 0.1 to 0.3 and the pre-0.4
  "everything nullable" branch are removed. No shipped spec uses them.

Deliberate non-goal: D5 keeps the TCP generation-policy code in core and only names it in the
spec, so the stream runtime still carries TCP-specific rules. Moving those rules out of core is
not attempted, and the "engine encodes format knowledge" bullet above is closed for builtins and
flow-field collisions, not for the generation policy.

Out of scope: early flushing of closed flows, bidirectional stream pairing, idle-timeout
splitting, cross-record keys (see [Open questions](#open-questions)), declarative framers, and
WASM components.

## Current evidence

Inspected at `c1a784b` (branch `feature/architecture-cleanup`). Line numbers refer to that
commit. Four claims (E3, E4, and both halves of E9(a)) were also checked by running small scratch
programs against the built `@byteql/core`; those are marked **(verified)**.

### E1. Framers name spec tables

- pcap's two root tables both anchor at the record root: `packets` and `interfaces` are each
  `rows: $` (`packages/formats/pcap/pcap.tables.yaml:13`, `:28`). Only the framer's `tables`
  restriction keeps a packet out of `interfaces` and an interface block out of `packets`:
  `tables: ['interfaces']` and `tables: ['packets']` at `packages/formats/pcap/src/framer.ts:57`,
  `:74`, `:113`, `:129`.
- MIDI does the same: `tables: ['header']` and `tables: ['events', 'tempo']` at
  `packages/formats/midi/src/framer.ts:164` and `:173`.
- `FramedRecord.tables` is an untyped `readonly string[]` (`packages/core/src/pack/framer.ts:18`).
  A typo projects nothing and fails no check, because `byteql-pack build` emits hook-name unions
  but no table-name union.
- The restriction costs per record. `session.project` allocates a `Set` of table names per call
  (`packages/core/src/projection/session.ts:93`). `projectInto` filters the root tables and
  builds a fresh matcher trie per call (`packages/core/src/projection/emit.ts:449-450`). For pcap
  that happens once per packet.

### E2. MIDI's sparse arrays reset state

- `events` and `tempo` anchor at `$.tracks[*].events.event[*]` with a `tick` register scoped
  `$.tracks[*]` (`packages/formats/midi/midi.tables.yaml:12-19`, `:77-85`).
- Registers reset only when the scope's wildcard indexes change
  (`packages/core/src/projection/emit.ts:144-151`), and a session keeps register state across
  `project()` calls. The prep design records this as contract: "callers projecting per-record
  roots must advance wildcard indexes across calls (sparse arrays, as the MIDI pack does) ...
  File-scoped (`$`) registers deliberately accumulate across calls"
  (`2026-07-18-phase1-generalization-prep-design.md:215-218`).
- The MIDI framer therefore builds `new Array(track.index + 1)` and fills only the last slot
  (`packages/formats/midi/src/framer.ts:169-170`). The array exists only to make `indexes[0]`
  differ per record. The `track` column then reads `_index(0)` (`midi.tables.yaml:21`), and the
  provenance resolver reads `anchor.indexes[1]` (`framer.ts:176`).
- The wildcard walk visits every hole (`packages/core/src/projection/walk.ts:78-80`), so track
  `n` costs `n` empty iterations: quadratic in the track count, though MIDI's track counts keep
  it small.

### E3. ZIP and pcap omit keys because a `null` anchor still matches

- Both walkers treat a present `null` as a match: `walkMatcher` recurses into any value that is
  not `missingProperty` (`walk.ts:65-66`, `:74-75`), and `traverseAnchor` does the same
  (`packages/core/src/projection/anchors.ts:112`, `:127`). Only a *missing* property stops a
  match.
- **(verified)** A `$.eocd` anchor over `{ eocd: null }` emits one row with every column null.
  Over `{}` it emits none.
- ZIP therefore omits `end_of_central_dir` instead of setting it to `null`, with a comment
  explaining why (`packages/formats/zip/src/framer.ts:9-18`). pcap's TLS wrapper does the same
  for a non-ClientHello record: `return { root: {} }` (`packages/formats/pcap/src/wrappers.ts:198-200`).
- This is the one documented exception to the "total roots" rule that strict-field conformance
  relies on (`docs/pack-authoring.md:151-160`).

### E4. TCP rules in the generic stream runtime

- `startsNewGeneration` (`packages/core/src/projection/stream-runtime.ts:198-207`) encodes TCP
  semantics: a repeated open offset is a retransmitted SYN (joins), and an open at the assembler
  base adopts a mid-stream flow. Nothing in the spec names this policy; it applies to every
  stream that declares `open`.
- The flow root is built as `{ ...entry.flowRoot, segment_count, byte_count, message_count,
  pending_bytes, status, opened, closed_by, generation, conflict_count }`
  (`stream-runtime.ts:657-668`). `entry.flowRoot` is the key extractor's `root`
  (`stream-runtime.ts:158`). **(verified)** A key extractor returning
  `{ status: 'FROM_KEY', generation: 99 }` loses both fields to the engine's `'ok'` and `1`, with
  no error at load or at runtime.
- The engine already rejects the equivalent collisions it can see statically: `stream_id` on
  stream-fed tables (`packages/core/src/projection/compile.ts:245-273`) and a feed key named
  like a fixed segments column (`compile.ts:810-823`).

### E5. Format builtins in core

- The closed builtin set is `enum_str`, `to_i`, `len`, `u24be`, `ip4_str`, `ip6_str`,
  `dos_dttm` (`packages/core/src/projection/expression.ts:90`), implemented at
  `expression.ts:639-670` and dispatched by `evaluateCall` (`expression.ts:672-694`).
- Four of them serve exactly one pack each: `u24be` (MIDI, `midi.tables.yaml:89`), `ip4_str` and
  `ip6_str` (pcap, `pcap.tables.yaml:47-48`), and `dos_dttm` (ZIP, `zip.tables.yaml:25`, `:50`).
- core also exports `formatIpv4` and `formatIpv6` (`packages/core/src/index.ts:33-34`). Their
  only non-test consumer is pcap's key extractor (`packages/formats/pcap/src/streams.ts:9`).
- Builtin names are checked in `validateCall` (`expression.ts:197-221`) against the global set,
  with exactly one argument (`expression.ts:213-215`). A new format helper therefore means a core
  release.

### E6. Engine-owned tables special-cased in four places

The segments and `errors` tables have no compiled definition. Each consumer rebuilds them:

1. **Session.** Builders for `compiled.tables`, then a second loop for `compiled.segmentsTables`
   (`session.ts:63-80`); `finish()` concatenates the two lists again (`session.ts:130-139`).
   The stream runtime keys segment ids by segments-table name (`stream-runtime.ts:135`).
2. **Schemas.** `projectionSchemas` maps projected tables, then segments tables, then builds an
   `errors` schema by instantiating an `IssueCollector` and reading its `table().types`
   (`packages/core/src/pack/schemas.ts:43-62`).
3. **Driver.** `errors` is assembled at EOF from `ParseIssue` objects into a `ProjectedTable` and
   converted with `projectedTableToArrow` (`packages/core/src/pack/driver.ts:128-142`). That is
   a second Arrow construction path beside `TableBatchBuilder`, which every other table uses.
4. **Build tool.** The query lint keeps its own `ENGINE_TABLES = ['errors', '_files']` and
   re-derives segments tables from the raw spec (`packages/pack-tools/src/queries.mjs:6`,
   `:49-55`).

Column order and types come from `tableOutputTypes` and `streamSegmentsOutputTypes`
(`compile.ts:890-917`); nullability comes from separate rules in `schemas.ts:17-32`.

### E7. Issues are unbounded and shipped twice

- `IssueCollector` appends every report to an array without a bound
  (`packages/core/src/issues.ts:30-56`). The driver keeps two collectors (framer and engine,
  `driver.ts:85-86`) and copies both into a third at EOF to impose framer-first order
  (`driver.ts:130-133`).
- The same issues then leave the worker twice: as the `errors` Arrow table, and as
  `SourceFinish.issues` (`packages/core/src/protocol.ts:88`), which the worker posts in its
  `finish` message (`apps/web/src/workers/parse.worker.ts:145`).
- The app shows at most 50 issues: `DIAGNOSTICS_CAP = 50`
  (`apps/web/src/components/Explorer.svelte:40-42`). It reads the full array only for its length.
- Packet-level failures (for example `DISSECT_PARSE_FAILED` per malformed packet) are
  recoverable by design, so a hostile capture can produce one issue per record, and all of them
  stay in memory until EOF.

### E8. Legacy spec versions

- The spec schema still accepts `0.1` to `0.5` (`packages/core/src/projection/spec.ts:83`,
  `:194-213`). It keeps version gates for `dissect`/`parent_key` (0.2), `streams` (0.3), and
  `nullable` (0.4) at `spec.ts:307-357`.
- `projectionSchemas` keeps a legacy branch that makes every spec column nullable before 0.4
  (`schemas.ts:29`, `:43`), and `CompiledColumn.nullable` is `boolean | undefined` for it
  (`compile.ts:28`).
- Every shipped spec is 0.4 or 0.5 (MIDI and ZIP `0.4`, pcap `0.5`), as is the
  `byteql-pack new` template (`packages/pack-tools/templates/__ID__.tables.yaml:1`). Only core
  tests still declare `0.1` to `0.3`.

### E9. Review items carried into this design

- **(a) Parent-key reachability is both too strict and too loose.**
  - *Too strict for message-table roots.* The reachability pass deliberately does not hop from
    a stream onto its message tables (`compile.ts:705-714`), so rule 7 (`compile.ts:756-772`)
    rejects a dissect rooted at a message table whose chain table parents onto the feed table.
    At runtime that key is present: message rows are emitted with the completing contribution's
    keys (`stream-runtime.ts:543-547`), and `emitRow` passes them on to its own dissects
    (`emit.ts:188-197`). **(verified)** `from: msg` is rejected with "parent_key.table "seg" is
    not reachable from "msg"". The equivalent `from: <message parser>` is accepted and fills the
    key.
  - *Too loose for shared parsers.* Reachability is a union over every path into a node
    (`compile.ts:727-754`). A parser fed from two root tables therefore "reaches" both, although
    each row reaches only one. **(verified)** A spec where parser `px` is fed from tables `a` and
    `b`, and `from: px` feeds `leaf` with `parent_key` onto `a`, compiles. The `leaf` row
    produced on the `b` path gets a null `a_id`, while `projectionSchemas` declares `parent_key`
    columns non-null (`schemas.ts:25`; contract in `docs/pack-authoring.md:204`). No shipped spec
    hits this.
- **(b) `OpenOptions.signal` is required** (`protocol.ts:65`), and so is `FramerContext.signal`
  (`framer.ts:25`). No framer reads it: only the driver does (`driver.ts:110`, `:146`, `:168`,
  `:182`). The app cancels by terminating the worker, so it passes a signal that is never aborted
  (`parse.worker.ts:68-69`, `:103`). The testing kit makes another (`packages/core/src/testing/collect.ts:54`).
- **(c) `STREAM_BELOW_BASE` now has two causes and one message.** Task 1 added a retained-history
  floor: a retransmission of bytes released by compaction is trimmed and reported through the
  same `trimmedBelowBase` flag (`packages/core/src/projection/streams.ts:252-263`). The runtime
  message said only "bytes before the reassembled start arrived after framing began"
  (`stream-runtime.ts:382-392`). For released history, the bytes are inside the stream, older
  than `max_buffer`. The cleanup's final review widened that one message to name both causes;
  the two causes still share one code.
- **(d) Flow memory.** Every flow entry lives until `finish()` (`stream-runtime.ts:117-130`,
  flushed at `:595-732`), so a SYN flood keeps one entry per SYN (ROADMAP.md priority 5,
  "Remaining limitations", `ROADMAP.md:100-106`). Separately, `StreamRuntimeEntry.segments`
  records every accepted contribution and every control segment until flush
  (`stream-runtime.ts:358-363`, `:421-426`), so a single long flow's metadata grows linearly
  even though Task 1's compaction now bounds its bytes.

## Goals and non-goals

Goals:

1. A framer says *what kind of record* it yields; the spec says which tables that kind feeds.
2. Per-record state reset is declared in the spec, not engineered with array indexes.
3. Roots are total everywhere: `null` means "absent" for anchors in v0.6 specs.
4. Format helpers are pack hooks, validated when the spec is compiled.
5. Engine field collisions are compile errors, and the stream generation policy is named.
6. One compiled list defines every output table: projected, flow, segments, and `errors`.
7. Issues are streamed as `errors` rows, and the summary handed to the app is bounded.
8. The spec version floor is 0.4.
9. Parent-key reachability is sound (a key the compiler accepts is a key the runtime fills),
   and admits message-table roots.
10. MIDI, ZIP, and pcap migrate with golden-identical output.

Non-goals: a static type check of `_.field` against `.ksy` types (PRD Appendix A's longer-term
"statically checkable" goal), user-defined functions in the DSL, and multi-argument builtins.

## Design

### D1. Record kinds

A root table may declare the kind of framed record it projects from:

```yaml
version: '0.6'
tables:
  - name: packets
    record: packet
    rows: $
  - name: interfaces
    record: interface
    rows: $
```

A framer yields the kind instead of table names:

```ts
yield { kind: 'packet', root, provenance };
```

Rules (`ProjectionCompileError`, new code `PROJECTION_RECORD_INVALID`):

- `record` requires `version: '0.6'` (`PROJECTION_VERSION_REQUIRED`).
- `record` is allowed only on root tables. A `parent_key` table or a stream flow table that
  declares it is rejected.
- **All or none.** If any root table declares `record`, every root table must. A spec with no
  kinds keeps today's behavior: every record is projected into every root table.
- Several tables may share a kind (MIDI's `events` and `tempo` both take `track`).
- Kind names are identifier-safe.

Runtime:

- `compileProjection` precomputes, per kind, the active root tables and their matcher trie, and
  one trie for the no-kinds case. `projectInto` stops building a trie per call (E1).
- `ProjectionSession.project(root, resolver, { kind })` replaces `{ tables }`. A record with an
  unknown kind, or with no kind when the spec declares kinds, throws; the driver already turns a
  `project()` throw into a recoverable `PROJECTION_FAILED` row (`driver.ts:153-163`).
- `byteql-pack build` emits a `RecordKind` string-literal union in `pack.generated.ts`, and
  `definePack` types the framer as `Framer<RecordKind>`, so a misspelled kind is a `tsc` error.
  It is the same mechanism the build already uses for hook names.
- `FramedRecord.tables` is kept while any pack still uses it, then removed once all three packs
  have migrated (slice S8). What that means for third-party 0.4/0.5 specs is an
  [open question](#open-questions).

### D2. Per-record state reset

A state register may declare `reset: record`:

```yaml
state:
  tick: { scope: $, reset: record, init: 0, update: 'tick + _.v_time.value' }
```

- **Semantics.** Before a table emits its first row within a `project()` call, every register
  with `reset: record` is re-initialized and its scope tracking cleared. Scope-driven resets still
  apply inside the record. Registers without `reset` keep the current contract: file-scoped
  (`$`) registers accumulate across records.
- **Implementation.** The session counts `project()` calls. `TableRuntime` stores the record
  number at which each such register last reset, and `emitRow`'s reset loop
  (`emit.ts:144-151`) compares it.
- **Rules.** Requires `version: '0.6'`. Rejected on `parent_key` tables, whose registers already
  reset per dissected payload (`emit.ts:406-413`).

The prep design's sentence about sparse arrays (`2026-07-18-...-design.md:215-218`) gets an
amendment note pointing here. The behavior it describes stays true for registers without
`reset`.

### D3. Null as "no match" on field and index steps

In a v0.6 spec, a field or index anchor step whose value is `null` or `undefined` matches
nothing, exactly like a missing property.

- **Applies to:** `walkMatcher` field and index steps (`walk.ts:64-76`) and `traverseAnchor` field
  and index steps (`anchors.ts:108-135`), so it covers root records and dissect child trees.
- **Wildcard steps are unchanged.** A `null` element of an array still yields a row. Whether
  wildcard elements should follow is an [open question](#open-questions). No shipped framer or
  wrapper was found to put `null` inside an anchored array.
- **Mechanism.** `compileAnchor` takes the spec version, and the compiled anchor carries one
  boolean (`nullIsAbsent`). All anchors in a projection share the spec's version, so the
  combined matcher reads one projection-wide flag.
- **Expressions are unaffected.** `_.x` reading a present `null` stays `null`. A missing field is
  still only a strict-mode finding.
- **Consequence for the authoring guide.** The "absent anchor" exception to total roots
  (`docs/pack-authoring.md:151-160`) is deleted. Roots are total without exception in v0.6.

### D4. Pack-registered builtins

Core keeps the format-neutral builtins: `enum_str`, `to_i`, `len`, and `_index`. Packs register
the rest as hooks:

```ts
definePack<Hooks>(definition, {
  // ...
  builtins: { ip4_str: formatIpv4, ip6_str: formatIpv6 },
});
```

- **Contract.** A builtin is a pure function `(value: unknown) => unknown` with the same
  never-throw rule as every row-time evaluation. The engine wraps each pack builtin call in a
  `try`/`catch` that yields `null`, so a buggy helper cannot break the engine invariant
  (AGENTS.md "Binding constraints").
- **Compile-time validation.** `compileProjection` takes a builtin registry next to the parser
  and stream registries. `compileExpression` takes the set of allowed names, and the compiled
  expression keeps a reference to the resolved function table, replacing the global dispatch at
  `expression.ts:693`. Any call to an unknown name fails at load with `EXPRESSION_CALL_FORBIDDEN`,
  as today.
- **Name rules.** A pack builtin must be identifier-safe and must not shadow a core builtin,
  `_index`, a context identifier, or a forbidden identifier (`expression.ts:90-125`). A state
  register named like a registered builtin is rejected at compile, extending the parse-time check
  at `spec.ts:253-259`, which only knows core names.
- **Build tool.** `byteql-pack build` collects call names that are not core builtins and emits a
  `BuiltinName` union. `PackHooks` gains `builtins: Record<B, Builtin>`, so a missing
  registration is a `tsc` error, and the build's placeholder registry
  (`packages/pack-tools/src/build.mjs:11-30`) covers builtins too. Core exports a small
  `getExpressionCallNames` helper beside `getExpressionStateReferences` for this.
- **Moves.** `ip4_str`/`ip6_str` (with `formatIpv4`/`formatIpv6`, deleted from core's public
  exports) go to pcap, `dos_dttm` to ZIP, and `u24be` to MIDI. This removal applies to every spec
  version: a 0.4/0.5 spec that calls one of them must now register it. The three shipped packs
  change in the same commit as core.
- **Arity stays one.** `dos_dttm(_.mod_date * 65536 + _.mod_time)` shows that a packed argument
  covers today's needs.

### D5. Flow-root collisions and the generation policy

**Collision rejection.** A key extractor declares the fields its `root` carries:

```ts
keyExtractors: {
  tcp_flow_key: { fields: ['src_addr', 'src_port', 'dst_addr', 'dst_port'], extract: tcpFlowKey },
},
```

- `compileProjection` rejects, with `PROJECTION_STREAM_INVALID`, any declared field that
  collides with an engine flow field: `segment_count`, `byte_count`, `message_count`,
  `pending_bytes`, `status`, `opened`, `closed_by`, `generation`, `conflict_count`. The list
  comes from one exported constant that `flushStreams` also uses to build the flow root
  (`stream-runtime.ts:657-668`).
- Once the flow root's shape is known at compile time, the compiler can also check each
  flow-table column's `_.<name>` reads against it, catching typos at load. This is optional
  within the slice, and cheap because the flow table's rows anchor is always `$`
  (`compile.ts:416-422`).
- **Runtime guard,** once per flow at creation (`stream-runtime.ts:158`). Fields the extractor
  returns but did not declare are dropped, never merged over engine fields. Under `strictFields`
  the undeclared field throws, so conformance finds the mismatch.

**Generation policy.** The rules in `startsNewGeneration` move into a named policy in a small
`stream-lifecycle.ts`. The spec names it:

```yaml
streams:
  - name: tls_stream
    open: _.syn
    generation_policy: connection   # the only value in v0.6; default when `open` is declared
```

- `connection` is exactly today's rule set: a repeated open offset joins; an open at the base of
  an unopened, unclosed generation adopts it; any other open starts a new generation.
- Declaring it is optional in v0.6 and defaults to `connection` when `open` is set, so pcap's
  output cannot change. `generation_policy` is a v0.6-only field, so it lands in S8 together with
  the `version: '0.6'` literal (`spec.ts:83`), not in S6. The point is that the spec now names the policy, and a second policy (a
  non-TCP connection protocol) is additive.
- Rejected alternatives are under [Alternatives considered](#alternatives-considered).

### D6. One `OutputTable` list

`compileProjection` returns `outputs: readonly OutputTable[]`, the single definition of every
table a session can emit:

```ts
interface OutputTable {
  readonly name: string;
  readonly kind: 'projected' | 'flow' | 'segments' | 'errors';
  readonly columns: readonly { name: string; type: ArrowTypeName; nullable: boolean }[];
}
```

- **Order** is what the engine emits today: spec tables in declaration order, then segments
  tables in first-use order (`compile.ts:856-863`), then `errors`. Column order and types are
  `tableOutputTypes`/`streamSegmentsOutputTypes` and the `errors` layout from `issues.ts:60-85`.
  Nullability is the rule set now in `schemas.ts:17-32`, `:47-61`, minus the legacy branch.
- **The `errors` ordinal column** becomes a compile option (`{ issues: { ordinalColumn } }`).
  The reserved-name check moves from `issues.ts:20-28` into the compiler.
- **Consumers:**
  - the session builds one `TableBatchBuilder` per output, `errors` included, and `finish()`
    walks the same list;
  - `projectionSchemas` becomes a projection of `outputs`;
  - the driver stops calling `projectedTableToArrow` for `errors`;
  - `byteql-pack build` lints queries against `outputs` plus the one app-owned table, `_files`.
- **`projectedTableToArrow` and `IssueCollector.table()`** lose their last production caller.
  `collectSource` in the testing kit (`testing/collect.ts:26`) still uses
  `projectedTableToArrow` for backfilled empty tables and can keep it as a test-only helper.
- **Golden safety.** Both paths already build vectors through the same `columnVector`
  (`packages/core/src/arrow/build.ts:295-327`, `packages/core/src/arrow/batch.ts:75-84`), so
  routing `errors` through `TableBatchBuilder` cannot change its Arrow bytes. The schema snapshot
  test (`packages/formats/pcap/test/schemas.snapshot.json` and its MIDI/ZIP equivalents) proves
  the list reproduces today's schemas exactly.

### D7. Streamed `errors`, bounded issue summary

- **One collector, report order.** The driver keeps a single sink for framer and engine issues.
  `error_id` is assigned when an issue is reported, and the row is appended straight to the
  session's `errors` builder. It drains at the flush threshold with every other table, so
  `errors` costs Arrow column memory, not one `ParseIssue` object per row kept to EOF in three
  copies.
- **Ordering contract change.** The pack-kit rule "framer-reported issues first, then engine
  issues" (`2026-09-23-pack-kit-design.md:273-275`) cannot survive streaming: an engine issue's
  `error_id` would depend on how many framer issues arrive later (pcap reports EOF truncation
  last, `framer.ts:77-78`). The new rule is **report order**.
  - No shipped golden changes: every `errors` table in the 20 goldens has zero rows or one row.
  - One unit test pins the old order (`packages/core/src/pack/driver.test.ts:81`) and is
    rewritten.
  - This is the one deliberate contract change in the design, and it is listed as an
    [open question](#open-questions) for confirmation.
- **Bounded summary.** `SourceFinish` becomes
  `{ issues: ParseIssue[] /* first N */, issueCount: number, capabilities }`. N defaults to 50,
  matching the Explorer's cap. The worker forwards `issueCount`, the Explorer header shows
  `issueCount` instead of `issues.length`, and the full detail lives only in the `errors` table,
  where SQL can reach it.
  - App-generated issues (`FILE_SKIPPED`, `apps/web/src/lib/session/intake.ts:230`) are added
    on the app side and are not capped by this.
  - **Multi-file sessions.** Intake concatenates each file's `result.issues`
    (`apps/web/src/lib/session/intake.ts:198`), and `Explorer.svelte:161-166` counts
    `session.issues.length`, which includes the app's `FILE_SKIPPED` issues. With the cap, each
    file keeps its first N issues and its `issueCount`. The session issue count becomes the sum of
    the per-file `issueCount` values plus the app-generated issues, and the Explorer list shows
    the concatenated capped entries. The app tests cover a two-file session where one file
    exceeds N and another file is skipped.
  - **Golden and conformance surface.** `issueCount` is added to `SourceFinish` and the worker
    message only. `ParseResult.issues` keeps its meaning (the capped summary list), so
    `goldenText` (`packages/core/src/testing/golden.ts:89`) serializes the same fields and no
    golden changes textually (all 20 have at most one issue, far below N). `collectSource` also
    asserts `issueCount >= issues.length`. The conformance issue comparison and chunk-invariance
    check (`conformance.ts:99-108`) hold because report order is chunk-size invariant: framer
    issues are reported at fixed stream positions (a record boundary or EOF), and engine issues
    are reported per record in document order, and neither depends on where chunk boundaries
    fall. A conformance test with a small and a large chunk size pins this.
- **Explorer table order.** Today the worker lists tables in first-batch order
  (`parse.worker.ts:120-128`). Because `errors` is always the last batch (`driver.ts:136-139`),
  it is always listed last among non-empty tables. A streamed `errors` batch could arrive
  earlier, so the worker orders its overview by `pack.schemas()` instead. That matches
  `outputs` order and is stable however batches interleave. The listing changes visibly only
  where a table's first batch used to arrive after a later-declared table's. The e2e suite is the
  check.
- **Unchanged:** the driver still emits a zero-row `errors` batch at EOF when nothing was
  reported (`driver.ts:138`), so `errors` always exists.

### D8. Minimum spec version 0.4

- `spec.ts` accepts `0.4`, `0.5`, `0.6`. Older versions fail with `PROJECTION_SPEC_INVALID`: "spec
  version 0.3 is no longer supported; the minimum is 0.4 (add `nullable: true` to columns that can
  be null)".
- Removed: the gates at `spec.ts:307-357` for `dissect`/`parent_key`, `streams`, and `nullable`
  (all now always available), the `legacy` parameter and branch in `schemas.ts`, and the
  `undefined` case of `CompiledColumn.nullable`.
- **Upgrading a spec from 0.1–0.3 to 0.4** has exactly one semantic step: 0.4 columns are
  non-null by default, so add `nullable: true` wherever a column can be null. The strict
  conformance nullability check finds any miss.
- **Tests.** Core tests with inline 0.1–0.3 specs are rewritten to 0.4. Tests that existed only
  to exercise the removed gates (parts of `spec-v02.test.ts` and `spec-v03.test.ts`) are
  deleted. The legacy-nullability case in `schemas.test.ts` is replaced by a "version too old"
  test.

### D9. Sound parent-key reachability with the message-table hop

Two changes to the shared fixpoint (`compile.ts:715-754`), checked together because each one alone
is either unsound or too strict:

1. **Must-reach.** A node's reachable set becomes the intersection over its incoming edges, not
   the union. The analysis seeds every node that has incoming edges at top (unknown) and
   intersects only over edges whose source has been visited; a topological pass works equally
   well, because the graph is acyclic by rule 11 (`compile.ts:326`). Seeding from empty sets, as
   `compile.ts:727-733` does for the union, would make every intersection empty and reject every
   spec. D9 supersedes the design comment at `compile.ts:712-714`, which argues against the
   message-table hop; that comment is rewritten with the change. A key is accepted only when every path that
   produces the row carries it. This
   turns the verified null-`parent_key` case in E9(a) into a load error, keeping the non-null
   schema promise. A scratch must-reach analysis of the three shipped specs found every
   `parent_key` still reachable on all paths, so no shipped spec is newly rejected.
2. **Message-table hop.** A stream folds its reachable set into each message *table* as well as
   each message parser, so a dissect rooted at a message table sees the feed-table keys it
   actually has at runtime.

Why both: with the hop alone, a message table that is also fed by a non-stream path (pcap's
`dns`, fed by `udp_datagram` and by `dns_tcp_stream`, `pcap.tables.yaml:168-171`, `:208`) would
union in keys that exist only on the stream path. Must-reach keeps only keys present on both. The
rule 7 and rule 9 error texts stay as they are; existing compile-error tests stay the oracle, and
new tests pin both changes.

### D10. Engine hygiene

- **Optional signal.** `OpenOptions.signal?: AbortSignal`. The driver's abort checks no-op
  without one. `FramerContext.signal` stays non-optional for framers, and the driver supplies one
  shared never-aborted signal when the caller passed none, so the framer contract does not change.
  `NEVER_ABORTED` in the parse worker and the fallback in `collect.ts:54` are deleted. The WIT
  sketch in PRD §9 has no signal at all, so this moves the TypeScript mirror closer to it.
- **Released-history retransmissions get their own code.** `AssemblerAddOutcome` splits
  `trimmedBelowBase` into:
  - `trimmedBelowBase`: below the locked base, `streams.ts:244-251`;
  - `trimmedReleased`: below the retained-history floor, `streams.ts:256-263`.

  The runtime reports the second as `STREAM_HISTORY_RELEASED`, once per flow with its own flag:
  "retransmitted bytes older than max_buffer (N) of history could not be compared and were
  dropped". `STREAM_BELOW_BASE` keeps its current meaning and message. No golden carries either
  code (every pcap `errors` golden is empty or a pcapng framing issue), and the one test that
  pins the released case (`streams.test.ts:378`) is updated.

### D11. Flow memory: what is in, what is out

- **Out of scope: early flush of closed flows.** Emitting a flow's `streams` row and its
  `stream_segments` rows when the flow closes would change row order in both tables and
  segment-id assignment, which today runs flow by flow at flush (`stream-runtime.ts:718-729`).
  That breaks the golden bar for every multi-flow fixture. It also needs its own semantics:
  - a late retransmission after flush, which today joins the closed generation, would open a new
    one;
  - keepalive classification (`ROADMAP.md:104-106`) interacts with it.

  It deserves its own design, as does streaming segment rows for long flows (E9(d), second
  point), which has the same ordering problem.
- **In scope, optional (slice S10): a live-flow cap.**
  - `compileProjection` takes an engine limit `maxLiveFlows` (default chosen by benchmark; for
    example 262 144 entries is about 300 MB at the measured ~1.2 KB per entry).
  - When a stream's live entries reach it, a contribution that would create a new flow is
    dropped, and one `STREAM_FLOW_LIMIT` issue is reported per stream.
  - Existing flows keep working. No fixture approaches the cap, so goldens are unaffected.
  - This turns the SYN-flood failure mode from "worker heap exhausted, session lost" into
    "bounded, reported loss".
  - Whether the cap is an engine constant or a spec field (`max_flows`) is an
    [open question](#open-questions).

### Spec surface summary (v0.6)

```yaml
version: '0.6'
format: midi
tables:
  - name: header
    record: header            # D1
    rows: $
    key: header_id
    columns: { ... }
  - name: events
    record: track             # D1
    rows: $.events[*]
    key: event_id
    state:
      tick: { scope: $, reset: record, init: 0, update: 'tick + _.v_time.value' }   # D2
    columns:
      track: { expr: _root.track, type: int32 }
      event_index: { expr: '_index(0)', type: int32 }
streams:
  - name: tls_stream
    generation_policy: connection   # D5, optional
```

The v0.6-only fields are `record`, `reset`, and `generation_policy`, plus the D3 null-anchor
semantics. Builtins (D4), flow-field collisions (D5), output tables (D6), issues (D7), the 0.4 floor
(D8), reachability (D9), and hygiene (D10) are version-independent engine changes.

## EVTX acceptance case

EVTX (ROADMAP.md priority 6) is the first pack written against v0.6. The acceptance test is: **an
EVTX pack scaffolded with `byteql-pack new evtx` reaches a passing `describePackConformance`,
including fuzz, with no edit to `packages/core`.** Below is what the pack needs from the
boundary, and which part of this design provides it.

| EVTX need | Provided by |
| --- | --- |
| A framer yielding a file-header record, one record per 64 KiB chunk header, and one per event record, each feeding different root tables | D1 record kinds (`file_header`, `chunk`, `event`), typed by the generated `RecordKind` union |
| An event's `EventData` name/value pairs as their own table, beside the `events` table, from the same record | D1 (two tables share kind `event`; `event_data` anchors at `$.data[*]`) |
| Optional sections (`UserData` instead of `EventData`, absent `Security` or `Correlation` elements) without omitted keys | D3 null anchors; roots stay total and strict conformance stays meaningful |
| FILETIME timestamps, GUIDs, and SIDs rendered in SQL-friendly form | D4 pack builtins (`filetime_us`, `guid_str`, `sid_str`), compile-checked and typed |
| A corrupted log (bad chunk CRCs, undecodable binary XML) producing one recoverable issue per record without unbounded memory | D7 streamed `errors` and capped summary |
| `pack.schemas()` and the query lint covering `errors` with no special cases | D6 output tables |
| A current spec version with no legacy branches to reason about | D8 |

What EVTX does **not** exercise, and why the design still carries it:

- Streams (D5, D10's released-history code, D11): pcap is their acceptance case, through its
  existing adversarial fixtures.
- Per-record reset (D2): MIDI is its acceptance case. EVTX's per-record values come from
  `_index` and the record root. A file-scoped register (for example the previous record's
  timestamp, for time deltas) is exactly today's accumulating behavior.

Two EVTX facts this design deliberately leaves to the EVTX pack design:

- How the framer decodes binary XML and chunk-scoped templates. PRD §13 names a Rust/WASM
  decoder; the framer contract does not care, but a bundled WASM asset must pass
  `check:bundle` and the no-runtime-loaded-code rule.
- How `events` references `chunks` (see the cross-record keys question below).

## Alternatives considered

- **Record kinds.**
  - *Keep `tables` and add a generated table-name union:* fixes typos, but the framer still
    encodes which tables a record feeds, which is spec knowledge, and the per-record `Set` and
    trie cost stays.
  - *Kinds declared in `pack.yaml` per container:* the mapping from kind to table belongs next to
    the tables in the spec, the only file that already knows them.
- **Per-record reset.**
  - *Change `$`-scoped registers to reset per record:* silently breaks the documented
    accumulate-across-calls contract for every existing spec.
  - *A framer flag (`FramedRecord.resetState`):* puts state semantics in code, against the
    data-first direction.
  - *A pseudo-anchor scope (`scope: '@record'`):* mixes two concepts into the anchor-prefix rule
    (`compile.ts:280-286`). A separate `reset` field leaves scope validation untouched.
- **Null anchors.**
  - *Make `null` absent for all versions:* the smallest code change, but it changes v0.4/v0.5
    behavior with no spec opt-in.
  - *Keep omission and document it:* leaves the only exception to total roots, which strict
    conformance cannot police.
- **Builtins.**
  - *Keep a versioned core library and add helpers per format as needed* (PRD Appendix A
    "versioned, closed function library", `PRD.md:248`): every new format becomes a core
    release, which is the leak this design closes. Pack builtins are no more code than the
    parsers packs already register, and are held to the same purity and never-throw contract.
  - *Multi-argument builtins:* not needed by any shipped or planned helper.
- **Flow-root collisions.**
  - *Namespace the flow root (`_.key.src_addr`, `_.flow.status`):* removes collisions
    structurally, but churns pcap's spec and needs a version-gated root shape, because v0.5 specs
    still load.
  - *Runtime-only detection:* not a compile-time guarantee, and the issue would fire per flow.
- **Generation policy.**
  - *A registered policy hook:* code for what is today one fixed rule set; additive later if a
    second protocol needs it.
  - *Leave it unnamed:* keeps a TCP rule invisible in the spec.
- **Issues.**
  - *Keep framer-first ordering by buffering:* engine `error_id`s depend on the final framer
    count, so `errors` could never be streamed.
  - *Drop the `ParseIssue[]` channel entirely:* the Explorer's diagnostics list would then need a
    DuckDB query at the end of every parse, a larger app change for the same bound.
- **Reachability.**
  - *Add only the message-table hop:* unsound for dual-fed message tables (D9).
  - *Leave it:* keeps both the false rejection and the false acceptance.
- **Version floor.**
  - *Raise to 0.6 after the migration:* removes the `tables` path and the null-anchor flag too,
    but rejects 0.4/0.5 specs with no external need for it yet. It is an open question.

## Migration plan

**Bar:** for every fixture of every pack, the golden (`test/goldens/*.golden.json`) and the schema
snapshot are byte-identical before and after. The conformance suite (`describePackConformance`)
keeps passing, including strict fields, chunk invariance, and fuzz. Goldens are not regenerated
during the migration; a diff fails the slice.

### ZIP (`0.4` to `0.6`)

1. `zip.tables.yaml`: `version: '0.6'`. No `record` declarations: ZIP yields one record and every
   root table takes it, which is today's behavior and v0.6's no-kinds case.
2. `src/framer.ts`: `end_of_central_dir: container.endOfCentralDir ?? null`, and the omission
   comment is deleted.
3. Register `dos_dttm` as a pack builtin (moved from core verbatim, with its tests).

Expected output change: none. `truncated-no-eocd.zip` still has zero `end_of_central_dir` rows,
now through D3 instead of omission.

### MIDI (`0.4` to `0.6`)

1. Header record: `kind: 'header'`, root `{ format, num_tracks, division }`, and the `header`
   table anchors at `$` with `record: header`.
2. Track records: `kind: 'track'`, root `{ track: track.index, events: safeEvents }`. The sparse
   array is gone.
3. `events` and `tempo`: `record: track`, rows `$.events[*]`, `tick` with `scope: $` and
   `reset: record`, `track: _root.track`, `event_index: _index(0)`.
4. Provenance resolver reads `anchor.indexes[0]` instead of `[1]`.
5. Register `u24be` as a pack builtin.

Expected output change: none. Keys are assigned in the same document order, `tick` resets at the
same boundaries, and `track` carries the same value. `malformed-then-valid.mid` and
`tempo-second-track.mid` are the sensitive fixtures: a skipped track and a non-first tempo track.

### pcap (`0.5` to `0.6`)

1. `packets`: `record: packet`; `interfaces`: `record: interface`. Framers yield
   `kind: 'packet'` and `kind: 'interface'`.
2. The TLS wrapper returns `{ client_hello: null }` instead of `{}`.
3. Register `ip4_str` and `ip6_str`. `formatIpv4`/`formatIpv6` move into the pack, shared by the
   builtin and `tcpFlowKey`.
4. `tcp_flow_key` already declares its four fields (done in S6). `generation_policy` may be left
   implicit.

Expected output change: none. Classic pcap's synthetic interface is still yielded first, so it
still receives `interface_id` 1, which every packet hard-codes (`framer.ts:69`).

**Performance check for pcap.** Precomputed per-kind matchers remove one trie construction and
one `Set` per packet, so classic 1 GB parse should improve or stay flat. One
`run-scale-bench.mjs --gb 1` run before and after slice S8's pcap step; a regression over 5% blocks
the step until explained.

## Testing

TDD for every behavior change; refactor slices (S2, S3) rely on the existing suites plus a
test only where a seam loses coverage.

- **Core, new tests:**
  - record-kind compile rules and dispatch, including a typo in a kind;
  - `reset: record` across two `project()` calls, with and without scope resets inside a record;
  - null-as-absent for field and index steps in v0.6, and unchanged behavior in v0.5 (the probe
    in E3, both ways);
  - builtin registry: unknown name, shadowing, a state name that collides with a builtin, and a
    throwing builtin evaluating to `null`;
  - flow-field collision and an undeclared runtime field under strict and non-strict modes;
  - `OutputTable` order equals the pre-refactor `finish()` and schema order;
  - streamed `errors` across drains with continuous `error_id`, and the capped summary with
    `issueCount`;
  - must-reach (the E9(a) "too loose" probe rejected) and the message-table hop (the "too
    strict" probe accepted, and its child row carrying the feed key);
  - `STREAM_HISTORY_RELEASED` versus `STREAM_BELOW_BASE`.
- **Packs:** conformance and goldens unchanged; one test per pack asserting the migrated root
  shape is total (no omitted anchor keys).
- **pack-tools:** generated `RecordKind` and `BuiltinName` unions; the query lint reads `outputs`.
- **App:** Explorer issue count from `issueCount` with more than 50 issues; table listing order
  from schemas; e2e suite green.
- **Optional S10:** a synthetic SYN-flood capture past the cap completes with one
  `STREAM_FLOW_LIMIT` row and bounded heap.

## Risks

- **Golden fidelity hides in ordering.** Output-table order, segment-id order, and `errors` order
  are all observable. Mitigation: S3 lands before any slice that could reorder, and the schema
  snapshot plus goldens are the oracle on every slice.
- **The `errors` ordering change is user-visible in principle.** No fixture shows it, but a
  capture that both truncates and fails a packet will now list the packet failure first.
  Mitigation: an explicit user decision (open question 1) and a CHANGELOG entry.
- **Must-reach could reject a third-party spec** that relied on the unsound union. No shipped spec
  does; the error names the unreachable table, and the fix (root the dissect at a table both paths
  share) is mechanical.
- **Removing core builtins breaks any external spec** that calls them. None exists outside this
  repository; the compile error names the missing builtin.
- **The live-flow cap drops data** on pathological captures. It is reported, optional, and
  sized by measurement.

## Open questions

1. **Errors ordering.** Accept report order (D7) in place of framer-first, so `errors` can be
   streamed? And accept the worker listing tables in schema order?
2. **Issue summary size.** Is N = 50 (the Explorer's current cap) right, and should it apply per
   file or per multi-file session?
3. **Wildcard nulls.** Should a `null` *element* under `[*]` also match nothing in v0.6, for full
   symmetry with D3? No shipped pack produces one, so either choice is golden-safe.
4. **`u24be`.** Move it to MIDI (as proposed), or keep a small format-neutral byte-decoding set in
   core (`u16be`, `u24be`, `u32be`, ...) that EVTX and others could share?
5. **Flow-root collisions.** Declared extractor fields (proposed) or a namespaced flow root?
6. **`FramedRecord.tables` after migration.** Remove it (proposed), which means a third-party
   0.4/0.5 spec with two `rows: $` root tables projects every record into both, or keep it for
   0.4/0.5 specs only?
7. **Version floor after migration.** Stay at 0.4, or raise to 0.6 once the three packs migrate?
8. **Live-flow cap (S10).** In or out of this cycle? If in: an engine constant or a spec
   `max_flows` field, and what default?
9. **Cross-record keys.** pcap already has a framer predict engine keys: `interface_id` equals
   the interface record's 1-based ordinal (`packages/formats/pcap/src/pcapng.ts:47`,
   `framer.ts:69`, `:93-94`). EVTX's events-to-chunks link would repeat the pattern. It holds
   only while every interface or chunk record emits exactly one row (no `where`, no projection
   failure). Should v0.6 add a declared cross-record reference, or should EVTX follow pcap's
   convention, documented as such?
10. **Generation policy field.** Name it in the spec now (proposed), or wait until a second policy
    exists?
